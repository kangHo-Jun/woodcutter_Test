# 재단 최적화 알고리즘 완전 가이드

## 0. 현재 정상 동작 상태 요약 (2026-05-20)

현재 `auto` 계산은 **한 가지 알고리즘만 쓰는 구조가 아니다.**
기본 알고리즘 A/B를 먼저 실행한 뒤, 더 좋은 결과를 만드는 **추가 후보(candidate)** 를 순서대로 비교해서 최종 결과를 고른다.

현재 최종 구조:

1. 알고리즘A 실행
2. 알고리즘B 실행
3. `RIP` 후보 비교
4. `MIXED_RIP` 후보 비교
5. `AREA_TARGET_HYBRID` 후보 비교
6. `GPP(guillotinePartitionPlanner)` 후보 비교
7. `SKINNY_ANCHOR` 후보 비교
8. `GROUP_SPLIT_2BIN` 후보 비교
9. **판재 수가 더 적고, 미배치가 없을 때만 채택**

즉 핵심 원칙은 단순하다.

- 기존 결과보다 **좋으면 채택**
- 같거나 나쁘면 **기존 결과 유지**

현재 검증된 대표 결과:

| 케이스 | 최종 결과 | 선택 엔진 |
|---|---:|---|
| CASE1 | 2장 | `AREA_TARGET_HYBRID` |
| CASE2 | 1장 | `GPP` |
| CASE3 | 1장 | `GPP` |
| CASE4 | 1장 | `SKINNY_ANCHOR` |
| CASE5 | 2장 | `GROUP_SPLIT_2BIN` |

이 문서는 “왜 이렇게 동작하는지”를 초보자 기준으로 설명한다.

## 4. 폭/길이 처리 방식 (중요!)

### 왜 복잡한가?
사용자가 폭(1220)을 첫번째로 입력할 수도 있고
길이(2440)를 첫번째로 입력할 수도 있음
→ 내부에서 항상 통일된 기준으로 처리 필요

### 처리 흐름
[사용자 입력]
boardWidth  = 첫번째 입력값 (1220 또는 2440)
boardHeight = 두번째 입력값
[main-unified.js: handleCalculate()]
packerW = Math.max(boardWidth, boardHeight)  → 항상 2440 (길이)
packerH = Math.min(boardWidth, boardHeight)  → 항상 1220 (폭)
packer = new GuillotinePacker(packerW, packerH, kerf)
[packer.js 내부]
width  = 2440 (길이방향, X축)
height = 1220 (폭방향, Y축)
[도면 렌더링: drawBinToCanvas()]
isPortraitBoard = false          ← 항상 가로 도면
renderBoardWidth  = Math.max()   ← 2440 (가로)
renderBoardHeight = Math.min()   ← 1220 (세로)
부품 좌표: x = 길이방향, y = 폭방향

### 나무결 고려 시
[main-unified.js: handleCalculate()]
boardLongIsX = true  ← 항상 true (packerW가 항상 길이방향)
부품 처리:
pw = Math.max(part.width, part.height)  ← 긴값 → 길이방향(X)
ph = Math.min(part.width, part.height)  ← 짧은값 → 폭방향(Y)
rotatable = false  ← 나무결 고려 시 회전 불가

## 5. 알고리즘A: 스트립 방식

**파일**: `js/packer.js`
**클래스**: `AdaptiveGuillotineBin`

### 동작 원리

가로/세로 방향 시뮬레이션 비교
→ simulateFirstDirection('H') vs simulateFirstDirection('V')
→ pickBetterSimulation()으로 더 나은 방향 선택
선택된 방향으로 스트립 생성
→ packHorizontalPrimary() 또는 packVerticalPrimary()
스트립 내 부품 배치
→ fillHorizontalStrip() - 높이 일치 부품만 배치
잔여 공간 재귀 처리
→ freeRects 순회하며 남은 부품 배치


### 핵심 함수
```javascript
// 방향 선택 기준 (pickBetterSimulation)
1. unplaced 없는 쪽 우선
2. unplaced 같으면 H(가로) 우선
3. placedArea 큰 쪽
4. score 높은 쪽

// 효율 점수 계산 (computeEfficiencyScore)
score = (배치면적/원장면적 × 100) - 슬리버패널티 - 단절패널티
```

### 장점 / 단점
장점: 다양한 부품 조합에 유연, 공간 효율 높음
단점: 긴 부품 배치 어려움, 짜투리 파편화

## 6. 알고리즘B: 길이절단 우선 방식 ⭐ 현재 주력

**파일**: `js/packer.js`
**함수**: `guillotineCutB(rect, items)`
**클래스**: `AdaptiveGuillotineBinB`

### 핵심 원칙
하부 짜투리 최소화 = 판재수 최소화 = 컷수 최소화

### 실제 절단 예시
입력 부품:
A: 820×750, B: 545×450, C: 205×450
D: 1270×50 ×2, E: 750×50 ×3
원장: 2440×1220
절단 순서:
┌─────────────────────────────┐
│ 원장 (폭1220 × 길이2440)    │
└─────────────────────────────┘
↓ 폭750 길이절단
┌─────────────────────────────┐
│ 상단 (폭750 × 길이2440)     │
└─────────────────────────────┘
↓ A 배치 후 우측 재귀
┌──────────┬──────────────────┐
│ A(820×750)│ 우측(750×1620)  │
└──────────┴──────────────────┘
↓ 폭450 길이절단
┌─────────────────┐
│상단(450×1620)   │→ B, C, E 배치
├─────────────────┤
│하단(300×1620)   │→ D 배치
└─────────────────┘
하단 짜투리: 폭470 × 길이2440

### guillotineCutB() 상세 동작
```javascript
guillotineCutB(rect, items) {
  // 1. rect에 들어갈 수 있는 부품 필터
  fittable = items.filter(아이템이 rect 안에 들어가는지)

  // 2. 높이 후보 수집 (item.height만, 회전 제외!)
  //    ⚠️ 회전 후보 추가하면 bestHeight가 커져서 짜투리 증가
  heightCandidates = fittable.map(item => item.height)

  // 3. 하부 짜투리 최소 높이 선택
  bestHeight = waste(rect.height - h)가 가장 작은 h

  // 4. 부품 배치 (면적 큰 순서, 좌→우)
  stripItems = bestHeight 이하 부품들 (면적 내림차순)
  for (item of stripItems) → placed에 추가

  // 5. 우측 잔여공간 → 재귀
  rightRect = {x: currentX+kerf, y: rect.y, w: 남은길이, h: bestHeight}
  guillotineCutB(rightRect, remaining)  ← fixedHeight 없음 (새 원장)

  // 6. 하단 잔여공간 → 재귀
  bottomRect = {x: rect.x, y: rect.y+bestHeight+kerf, w: rect.w, h: 남은폭}
  guillotineCutB(bottomRect, remaining)  ← 새 원장
}
```

### ⚠️ 수정 시 주의사항

**heightCandidates 수집:**
```javascript
// ✅ 올바른 방법 (item.height만)
fittable.forEach(item => {
    if (item.height <= rect.height && item.width <= rect.width) {
        heightCandidates.add(item.height);
    }
});

// ❌ 잘못된 방법 (회전 포함하면 bestHeight 증가)
// item.width도 추가하면 안 됨!
```

**재귀 시 fixedHeight:**
```javascript
// ✅ 올바른 방법 (새 원장 = fixedHeight 없음)
guillotineCutB(rightRect, remaining)

// ❌ 잘못된 방법
guillotineCutB(rightRect, remaining, bestHeight)  // fixedHeight 전달 금지
```

### ⚠️ 회전 처리 주의사항

**회전 후보 등록 조건:**
```javascript
// 회전 시 height가 더 작아지는 경우만 추가
if (item.rotatable &&
    item.width < item.height &&      // 회전하면 height가 작아짐
    item.width <= rect.height &&     // 회전 후 height ≤ rect.height
    item.height <= rect.width) {     // 회전 후 width ≤ rect.width
    heightCandidates.add(item.width);
}
```

**예시:**
500×1400 부품 (rotatable=true):

원래: height=1400 > rect.height(1220) → 등록 안 됨
회전: width(500) < height(1400) ✅
width(500) ≤ rect.height(1220) ✅
height(1400) ≤ rect.width(2440) ✅
→ item.width(500) 등록 → 배치 가능!


### ⚠️ 알고리즘 선택 기준

```javascript
if (binsB.length === 0) → A 선택  // B가 배치 못하면 A 사용
if (binsA.length === 0) → B 선택  // A가 배치 못하면 B 사용
if (binsA < binsB)     → A 선택  // A가 더 효율적
else                   → B 선택  // 같거나 B가 효율적
```

## 7. 알고리즘 선택 로직

**파일**: `js/packer.js`
**함수**: `packAdaptiveAuto()`

```javascript
// 1. 기본 엔진 2개 실행
binsA = AdaptiveGuillotineBin으로 배치
binsB = AdaptiveGuillotineBinB으로 배치

// 2. 기본 결과 선택
// 우선순위:
// 미배치 수 → 판재 수 → 절단 횟수

// 3. 추가 후보 비교
RIP
MIXED_RIP
AREA_TARGET_HYBRID
GPP
SKINNY_ANCHOR

// 4. 최종 채택 규칙
// 더 좋은 결과일 때만 교체
```

### 7-1. 왜 후보를 여러 개 돌리는가?

한 가지 heuristic만으로는 모든 케이스를 잘 풀 수 없다.

- `CASE1`은 큰 부품 `G(595×595)` 공간을 미리 남겨야 한다
- `CASE4`는 얇고 긴 `D(770×100)×2` 공간을 미리 확보해야 한다

즉 케이스마다 “잘 맞는 전략”이 다르다.
그래서 현재 구조는 **기본 엔진 + 특수 후보 비교** 방식으로 바뀌었다.

### 7-2. 현재 각 후보의 역할

#### A / B
- 기존 기본 엔진
- 빠르고 안정적
- 하지만 특정 병목 부품을 끝까지 못 살리는 경우가 있음

#### AREA_TARGET_HYBRID
- 목표 판재 수를 먼저 계산하고
- 가로/세로 관통 절단을 섞어서 탐색
- `CASE1`처럼 면적상 2장이 가능한 케이스를 줄이는 데 유리

#### GPP
- `guillotinePartitionPlanner`
- shallow recursive + beam search 기반
- `CASE2`, `CASE3`처럼 회전이 핵심인 단순 반복 케이스에 강함

#### SKINNY_ANCHOR
- `CASE4` 전용 성격이 강한 후보
- 얇고 긴 반복 부품을 먼저 코너에 고정(anchor)
- 남은 영역에 나머지 부품을 배치
- 현재는 `D(770×100)×2` 같은 부품 해결용

#### GROUP_SPLIT_2BIN
- 혼합 입력 전용 후보
- `id` 기준으로 부품 그룹을 나눔
- 각 그룹을 단독 `auto`로 실행
- 각 그룹이 `1장`, `unplaced=0`이면 결과를 합쳐 채택
- 현재는 `CASE5` 같은 “섞으면 3장, 분리하면 2장” 케이스 해결용

### 7-3. 현재 최종 채택 규칙

추가 후보는 아무 때나 채택하지 않는다.

- `unplaced = 0` 이어야 함
- 판재 수가 더 적어야 함
- 같거나 더 나쁘면 버림

이 방어 로직 때문에
새 후보를 추가해도 기존 성공 케이스를 망가뜨릴 가능성을 줄일 수 있다.

## 8. CASE1~5가 현재 어떻게 해결되는가

### CASE1

입력:
- `A(390×745)×3`
- `B(405×645)×5`
- `C(295×790)×2`
- `D(295×745)×2`
- `E(295×645)×4`
- `F(295×535)×2`
- `G(595×595)×1`

문제 핵심:
- 기본 A/B만 돌리면 `G(595×595)`가 마지막에 3번째 판재로 밀린다

해결 엔진:
- `AREA_TARGET_HYBRID`

이유:
- 목표 판재 수 2장을 먼저 정하고
- 공간을 더 전역적으로 탐색해서
- `G`가 들어갈 블록 공간을 남기는 배치를 찾는다

### CASE2

입력:
- `600×900 ×5`

문제 핵심:
- 회전 허용 시 1장 가능
- 단순 greedy는 마지막 1개를 잃기 쉬움

해결 엔진:
- `GPP`

이유:
- recursive partition 탐색으로
- `1 + 2 + 2` 구조를 만들 수 있다

### CASE3

입력:
- `400×1000 ×7`

문제 핵심:
- 회전 허용 시 1장 가능
- beam search가 충분히 살아야 함

해결 엔진:
- `GPP`

이유:
- 반복 구조가 단순해서
- shallow recursive guillotine 탐색에 잘 맞는다

### CASE4

입력:
- `A(397×596)×4`
- `B(771×286)×4`
- `C(600×285)×4`
- `D(770×100)×2`

문제 핵심:
- 기본 엔진은 `D` 2개 중 마지막 1개가 밀린다
- 이유는 `A/B/C`를 먼저 채우면서 `D×2` 공간이 사라지기 때문

해결 엔진:
- `SKINNY_ANCHOR`

이유:
- `D`를 “나중에 넣는” 것이 아니라
- 처음부터 코너에 먼저 고정한다
- 그리고 남은 두 개의 직사각형 영역에 `A/B/C`를 배치한다

### CASE5

입력:
- `A(900×600)×5`
- `B(400×1000)×7`

문제 핵심:
- `A` 단독은 `1장`
- `B` 단독도 `1장`
- 그런데 둘을 한 번에 넣으면 기존 heuristic은 `3장`

해결 엔진:
- `GROUP_SPLIT_2BIN`

이유:
- 이 케이스는 섞어 배치하는 것보다
- `A` 그룹 한 장
- `B` 그룹 한 장
으로 나누는 것이 정답이다
- 그래서 그룹별로 먼저 `auto` 성공 여부를 보고, 둘 다 `1장`이면 합쳐서 `2장`으로 채택한다

## 9. SKINNY_ANCHOR 쉽게 이해하기

### 언제 발동하나?

아래 조건을 만족할 때만 시도한다.

1. 전체 부품 면적이 판재 1장 면적 이하
2. skinny 부품 존재
   - `longSide / shortSide > 5`
   - `qty >= 2`

현재 `CASE4`의 `D(770×100)×2`가 여기에 해당한다.

### 무엇을 하느냐?

예를 들어 `D(770×100)×2`이면,

- 긴 변: `770`
- 짧은 변: `100`
- 수량: `2`

따라서 필요한 예약 높이는

`100 + kerf + 100 = 204.2`

즉 `770 × 204.2` 크기의 anchor 공간을
판재 한쪽 코너에 먼저 확보한다.

그 다음:

- 남은 큰 직사각형 1개
- 남은 작은 직사각형 1개

에 대해 기존 `AdaptiveGuillotineBin.packRectFlexible()`를 사용해 나머지 부품을 배치한다.

### 왜 guillotine 규칙을 지키는가?

anchor는 코너에 둔다.
그러면 절단은 항상 관통 2번으로 표현할 수 있다.

예: `bottom-right`

1. 세로 관통 절단
2. 오른쪽 strip에서 가로 관통 절단

즉 중간 정지 절단 없이 구현 가능하다.

## 10. GROUP_SPLIT_2BIN 쉽게 이해하기

### 언제 필요한가?

어떤 입력은 한 판재 안에 섞으려는 시도보다
아예 그룹을 분리하는 것이 훨씬 낫다.

`CASE5`가 대표적이다.

- `900×600 ×5`는 단독 `1장`
- `400×1000 ×7`도 단독 `1장`
- 하지만 같이 넣으면 기본 엔진은 `3장`

### 현재 발동 조건

1. `id` 기준 그룹이 2개 이상
2. 현재 구현에서는 조합 폭발 방지를 위해 **정확히 2개 그룹만 처리**
3. 각 그룹을 단독 `auto` 실행했을 때
   - `bins = 1`
   - `unplaced = 0`
4. 합친 결과가 현재 선택 결과보다 더 좋아야 함

### 왜 `id` 전달이 중요하나?

이 후보는 `width/height`가 아니라 **`id` 기준 그룹**을 사용한다.
그래서 브라우저 경로에서 `main-unified.js`가 packer 입력을 만들 때
`id`를 함께 넘겨야 한다.

현재는 아래처럼 전달하도록 보완되어 있다.

```javascript
return {
  id: part.id,
  width: pw,
  height: ph,
  qty: part.qty,
  allowRotate: effectiveAllowRotate
};
```

## 16. 쭉절단 우선 배치/비용 판정 개선 이력 (2026-04-17)

### 수정 배경

#### 문제 케이스
- 판재: 폭 `1220` × 길이 `1000`
- 부품:
  - `90 × 1000` 수량 6
  - `130 × 1000` 수량 3
- 나무결 방향 고려: OFF
- 부품 회전: 가능

#### 기존 결과
- 부품이 `90×1000`, `130×1000` 형태 그대로 세워져 좌→우로 나열됨
- 절단선은 세로선(`axis: 'X'`) 위주로 생성됨
- 총 절단비는 일반 절단비 기준으로 계산됨
- 예: `9회 × 1,500원 = 13,500원`

#### 기대 결과
- 회전 가능한 부품이므로 `1000×90`, `1000×130`으로 돌려 배치
- 판재 길이 `1000`을 전체로 사용하는 가로 쭉절단 패턴이 됨
- 쭉절단 고정비가 일반 절단비보다 저렴하면 쭉절단 비용 적용
- 예: 일반 절단비 `13,500원`보다 쭉절단 고정비 `10,000원`이 저렴하므로 `10,000원` 적용

### 핵심 좌표계

현재 packer 내부 좌표계는 아래처럼 사용한다.

```text
판재 입력:
- boardWidth  = 폭
- boardHeight = 길이

packer 내부:
- binWidth  = boardHeight = 길이 방향 = X축
- binHeight = boardWidth  = 폭 방향 = Y축

도면 렌더링:
- 도면 가로 = boardHeight = 길이
- 도면 세로 = boardWidth  = 폭
```

예를 들어 판재가 `폭 1220 × 길이 1000`이면:

```text
packer width  = 1000
packer height = 1220
```

따라서 길이 전체를 쓰는 쭉절단선은 아래 조건을 만족해야 한다.

```javascript
cut.axis === 'Y'
cut.spanStart === 0
cut.spanEnd === bin.width
```

주의:
- `axis: 'Y'`는 "Y 위치에서 가로로 긋는 선"이다.
- 즉 실제 도면에서는 길이 방향 전체를 가로로 관통하는 절단선이다.
- `axis: 'X'` 절단선이 섞이면 그 판재는 쭉절단 비용 대상이 아니다.

### 수정 파일 1: costCalculator.js

#### 함수

```javascript
CostCalculator.getLongSidePanelFixedPrice(bin)
```

#### 기존 문제

기존에는 `cutDetails.fullSpan === true` 값에 의존했다.

```javascript
if (bin.cutDetails.some(detail => detail && detail.fullSpan !== true)) {
    return 0;
}
```

하지만 알고리즘B(`guillotineCutB`)에서 직접 생성하는 `cutDetails`에는 `fullSpan` 값이 없는 경우가 있었다.

```javascript
cutDetails.push({
    axis: 'Y',
    pos: ...,
    spanStart: ...,
    spanEnd: ...
});
```

그래서 실제로는 길이 전체를 관통하는 쭉절단선이어도 `fullSpan: undefined` 때문에 쭉절단 비용이 적용되지 않았다.

#### 개선 후 기준

`fullSpan` 필드 대신 실제 좌표를 보고 판단한다.

```javascript
const lengthSpan = Number.isFinite(bin.width) ? bin.width : maxSpanEnd;
const isLongRipCut = detail => detail
    && detail.axis === 'Y'
    && Math.round(detail.spanStart) === 0
    && Math.round(detail.spanEnd) === Math.round(lengthSpan);

if (bin.cutDetails.some(detail => !isLongRipCut(detail))) {
    return 0;
}
```

#### 의미

쭉절단 비용이 적용되려면:
- 모든 절단선이 `axis: 'Y'`
- 모든 절단선이 `0 ~ bin.width` 전체를 관통
- 중간 절단선, 세로 절단선, 부분 절단선이 하나라도 있으면 제외

즉 한 판재 안에 일반 절단이 섞이면 쭉절단 비용을 적용하지 않는다.

### 수정 파일 2: packer.js

#### 변경 1: bin 결과에 width/height 추가

비용 계산에서 현재 판재 길이를 정확히 알 수 있도록 bin 결과 객체에 `width`, `height`를 추가했다.

이 값이 없으면 `costCalculator.js`에서 `spanEnd` 최대값으로 추정해야 하는데, 부분 절단만 있는 특수 케이스에서 오판 가능성이 있다.

#### 변경 2: 자동 배치에서 RIP 후보 추가

자동 모드(`packAdaptiveAuto`)는 기존처럼 알고리즘A와 알고리즘B를 먼저 실행한다.

```text
1. 알고리즘A 실행
2. 알고리즘B 실행
3. 판재 수 비교
4. 같으면 B 선택
```

그 다음 별도 쭉절단 후보를 만든다.

```javascript
const ripCandidate = this.buildLengthRipCandidate(expandedItems);
if (ripCandidate && this.shouldPreferLengthRip(ripCandidate, selectedBins, selectedUnplaced)) {
    selectedBins = ripCandidate.bins;
    selectedUnplaced = ripCandidate.unplaced;
    selectedEngine = 'RIP';
}
```

#### 새 함수 1: buildLengthRipCandidate(items)

역할:
- 모든 부품이 현재 판재 길이 전체를 쓰는지 검사
- 가능하면 `1000×90`, `1000×130` 같은 가로 쭉절단 배치를 직접 생성
- 절단선은 모두 `axis: 'Y'`, `spanStart: 0`, `spanEnd: this.binWidth`로 생성

동작 방식:

```text
1. 각 부품이 길이 전체를 쓸 수 있는지 검사
2. 회전 가능하면 회전 배치도 검사
3. 위에서 아래로 한 줄씩 쌓음
4. 판재 높이를 넘으면 다음 판재로 넘김
5. 모든 절단선을 길이 전체 관통선으로 생성
```

예:

```text
입력 부품:
- 90×1000
- 130×1000

판재 내부 길이:
- binWidth = 1000

회전 후 배치:
- 1000×90
- 1000×130
```

#### 새 함수 2: getLengthRipOrientation(item)

역할:
- 한 부품이 쭉절단 후보가 될 수 있는지 판단

통과 조건:

```text
조건 A:
- item.width === binWidth
- item.height <= binHeight

조건 B:
- item.rotatable === true
- item.height === binWidth
- item.width <= binHeight
```

조건 B가 바로 이번 문제 케이스다.

```text
90×1000
→ item.height === binWidth(1000)
→ 회전 가능
→ 1000×90 배치 가능
```

#### 새 함수 3: shouldPreferLengthRip(ripCandidate, selectedBins, selectedUnplaced)

역할:
- 기존 A/B 결과와 RIP 후보를 비교해 RIP를 선택할지 결정

선택 조건:

```text
1. RIP 후보가 존재해야 함
2. RIP 후보에 unplaced가 없어야 함
3. RIP 후보의 판재 수가 기존 선택보다 많으면 선택하지 않음
4. 판재 수가 더 적으면 RIP 선택
5. 판재 수가 같으면 비용 비교
6. 쭉절단 고정비가 실제로 적용되고, RIP 비용이 기존 비용보다 저렴하면 RIP 선택
```

즉 쭉절단이 가능하다고 무조건 RIP를 선택하지 않는다.
비용이 더 저렴할 때만 선택한다.

### 다음 개발자가 주의할 점

#### 1. RIP 후보는 단순 쭉절단 전용이다

현재 RIP 후보는 모든 부품이 판재 길이 전체를 쓰는 경우만 다룬다.

가능:

```text
90×1000, 130×1000 on 1220×1000
→ 1000×90, 1000×130으로 회전
```

불가능:

```text
700×450, 300×200 같은 일반 혼합 부품
```

혼합 부품까지 RIP로 억지 선택하면 기존 최적화가 망가질 수 있으므로 확장 시 조건을 매우 좁게 유지해야 한다.

#### 2. 비용 계산은 배치 선택 후에 한다

기본 구조:

```text
packer.js
→ 배치 결과 생성

costCalculator.js
→ 생성된 배치의 cutDetails를 보고 비용 계산
```

이번 수정은 예외적으로 `packer.js` 내부에서 `CostCalculator.calculate()`를 사용해 RIP 후보와 기존 후보의 비용을 비교한다.

이 비교는 `shouldPreferLengthRip()` 안에서만 수행한다.

#### 3. cutDetails가 실제 배치와 맞아야 한다

절단선만 바꿔서는 안 된다.

예를 들어 `90×1000` 부품을 실제로는 세로 배치해 놓고, 절단선만 가로 쭉절단으로 바꾸면 도면과 실제 절단이 맞지 않는다.

따라서 RIP 선택 시에는:
- `placed`도 `1000×90`처럼 회전된 상태
- `cutDetails`도 `Y` 관통선
- `costCalculator`도 쭉절단 비용

이 세 가지가 동시에 맞아야 한다.

#### 4. 쭉절단 비용 적용 제외 조건

아래 중 하나라도 있으면 쭉절단 비용 제외:

- `axis: 'X'` 절단선 존재
- `axis: 'Y'`라도 `spanStart !== 0`
- `axis: 'Y'`라도 `spanEnd !== bin.width`
- 중간 부분 절단선 존재
- 일반 혼합 배치

```text
4. 해당 패턴의 freeRects에 일반 부품을 packRectFlexible()로 재배치
5. 남은 일반 부품만 기존 A/B로 배치

```

쭉절단 고정비가 적용되는 RIP 패턴은 보존한다.

```javascript
if (window.CostCalculator.getLongSidePanelFixedPrice(bin) > 0) return;
```

- 고정비가 적용되는 순수 쭉절단 패턴에 일반 부품을 넣으면 일반 절단선이 섞인다.
- 그러면 해당 패턴의 쭉절단 고정비가 사라질 수 있다.
- 따라서 고정비가 적용되지 않는 RIP 패턴에만 일반 부품 삽입을 시도한다.

#### 개선 후 예시 결과

### 17-5. 회전불가 부품 좌표 변환 수정

#### 파일

```text
js/main-unified.js
함수: handleCalculate()
```

#### 문제

packer 내부 좌표계는:

```text
X축 = 판재 길이
Y축 = 판재 폭
```

그런데 나무결 OFF + 회전불가 부품에서 기존에는:

```text
part.width  → packer width(X)
part.height → packer height(Y)
```

로 그대로 넘겼다.

예:

```text
판재: 폭1220 × 길이1000
부품: 1200 × 1000
회전불가
```

물리적으로는 가능:

```text
폭 1200 <= 1220
길이 1000 <= 1000
```

하지만 packer에는 `width=1200`, `height=1000`으로 들어가서:

```text
X=1200 > 판재 길이 1000
```

로 판단되어 미배치될 수 있었다.

#### 수정

나무결 OFF + 회전불가일 때는 packer 좌표계에 맞게 변환한다.

```javascript
const pw = considerGrain
    ? Math.max(part.width, part.height)
    : (!part.rotatable ? part.height : part.width);

const ph = considerGrain
    ? Math.min(part.width, part.height)
    : (!part.rotatable ? part.width : part.height);
```

의미:

```text
회전불가 부품:
part.height → packer width(X, 길이)
part.width  → packer height(Y, 폭)
```

#### 검증

```text
판재: 1220×1000
부품: 1200×1000
회전불가
전단 OFF
```

결과:

```text
bins=1
unplaced=0
```

### 17-6. 전단 설정 저장 버그 수정

#### 파일

```text
js/settingsManager.js
함수: validateSettings()
```

#### 문제

기존에는 설정 검증 시 전단을 항상 ON으로 강제했다.

```javascript
validated.enableTrim = true;
```

문제:
- UI에서 전단 OFF로 계산해도 저장/복원 과정에서 ON으로 바뀔 수 있다.

#### 수정

```javascript
validated.enableTrim = typeof settings.enableTrim === 'boolean'
    ? settings.enableTrim
    : this.DEFAULT_SETTINGS.enableTrim;
```

#### 검증

```text
enableTrim false preserved: true
enableTrim true preserved: true
```

### 17-7. 회전/나무결/절단 횟수 정책 정리

#### 현재 정책

나무결 ON:

```text
부품 긴 치수 → 판재 길이 방향
부품 짧은 치수 → 판재 폭 방향
rotatable=false
```

나무결 OFF:

```text
rotatable=true인 부품은 회전 후보 허용
일반 A/B 배치, 순수 RIP, 혼합 RIP 후보 모두 검토
```

자동 선택 목적함수:

```text
1. 미배치 최소
2. 판재 수 최소
3. 절단 횟수 최소
4. RIP/MIXED_RIP는 비용이 더 낮을 때 선택
```

주의:
- 나무결 OFF가 항상 나무결 ON보다 절단 횟수가 적다는 보장은 없다.
- 하지만 회전 후보가 많아지므로 더 좋은 후보를 찾을 가능성이 높다.
- 현재 구조상 일반 A/B는 절단 횟수 비교가 들어갔지만, 세부 strip 내부 회전 선택은 여전히 면적/부품 수 중심이다.

### 17-9. 다음 개발 시 주의사항

1. `tryPlaceResidualInAdaptive()`에서 직접 `placed.push()`를 다시 도입하지 말 것
2. freeRect에 부품을 넣을 때는 반드시 `packRectFlexible()` 또는 동등한 freeRect 분할 로직을 사용할 것
3. 새 후보 알고리즘을 추가하면 반드시 `isValidPackingResult()`를 통과시킬 것
4. A/B 선택 기준을 바꿀 때는 아래 순서를 유지할 것

```text
unplaced
→ bins
→ cuttingCount
→ tie-break
```

5. RIP/MIXED_RIP는 “공간에 들어간다”가 아니라 “총 비용이 낮다”를 기준으로 선택할 것
6. 전단 ON/OFF는 `SettingsManager.validateSettings()`에서 보존되어야 한다
7. 나무결 ON에서는 `rotatable=false`가 되어야 하며, 기존 방향 고정 정책을 깨지 말 것
